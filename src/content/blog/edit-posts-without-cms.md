本网站完全是ai构建，当我想要新增，删除或修改内容时，我不知道具体流程。因此，身为懒人的我，让ai帮我写一篇文章，教我如何操作。这真是懒人福利。

## 文件在哪

| 内容 | 路径 |
| --- | --- |
| 博客文章 | `src/content/blog/` |
| 短想法 | `src/content/notes/` |
| 文章图片 | `public/images/` |

一篇文章一个 `.md` 文件，文件名就是网址。`reading-slowly.md` 对应的地址是 `/blog/reading-slowly/`，所以**改文件名等于改网址**，旧链接会直接 404。想改标题就改 frontmatter 里的 `title`，别动文件名。

## 新增一篇

在 `src/content/blog/` 下新建文件，开头写 frontmatter：

```markdown
---
title: 文章标题
description: 一句话摘要，列表和搜索结果里会显示
pubDate: 2026-11-17
tags: ['写作', '方法']
draft: false
---

正文……
```

字段由 `src/content.config.ts` 校验，写错类型构建会直接失败，倒也不用担心文章悄悄带着坏数据上线。三个最常错的点：

- `pubDate` 必须是 `2026-11-17` 这种格式，写成 `2026/11/17` 会报类型错误。
- YAML 缩进只能用空格，不能用 Tab。
- 冒号必须是半角 `:`，中文冒号会让整个 frontmatter 解析失败。

图片放进 `public/images/`，正文里用 `/images/xxx.png` 引用。这个目录不存在就新建一个，构建时会原样复制到输出目录。

写到一半的东西，就加一行 `draft: true`。草稿只在本地 `npm run dev` 时可见，构建时会被排除，不会出现在列表、RSS 和站内搜索里。

## 修改一篇

打开对应的文件改文字，然后提交。就这么简单。

只有一件事要注意：**别顺手改 `pubDate`**。列表按它倒序排，改一次，旧文章就会跳到最前面，像刚发的一样。修错别字就只改错别字。

如果确实有实质更新，加一行 `updatedDate: 2026-11-17`，文章页会显示「更新于」，比篡改发布日期诚实，也更符合读者预期。

还有一种需求是「先下线，但不想删」。把 `draft` 改成 `true` 即可：文件还在，本地还能打开，线上那条链接和列表项会一起消失。

## 删除一篇

删掉 `src/content/blog/` 里那个 `.md`，再去 `public/images/` 清掉只被它引用的图片。

删除是这里唯一不可逆的操作，两个副作用要提前想清楚：

1. 旧网址会变成 404。别人引用过它、搜索引擎收录过它，链接就断了。
2. 如果别的文章里还链向它，构建不会报错——Static 站不做全站链接检查——上线后才会发现死链。

所以真正想「撤回」而不想「销毁」时，我优先用 `draft: true`。如果内容是彻底过时了，但那个链接还有人访问，可以留一篇文章说明「这篇已合并到某处」，把旧地址当作一个路标，而不是直接拆掉。

## 发布

本地先看一遍：

```bash
npm run dev      # 浏览器里点一遍文章、标签、RSS
npm run build    # 有报错会打印到文件和行号
```

确认没问题就提交：

```bash
git add src/content/blog/
git commit -m "新增：如何新增，删除或修改内容"
git push
```

推送后由 GitHub Actions 构建，大约一分钟上线。构建失败会停在 Actions 页面，线上仍是上一版，不会出现半截的站点。

## 为什么不做后台

后台最诱人的地方是「所见即所得」，但代价是数据库、登录、权限、备份、依赖升级，还有半夜被告知插件有漏洞的可能性。这些成本平时看不见，等到某天不想写了，它们会一起出现。

用文件也有代价：没有自动保存，没有草稿箱，手机上改文章很别扭。所以我把草稿箱换成了 `draft` 字段，把版本历史交给了 git——写坏了就回滚，比任何「撤销」按钮都彻底。

工具应该让人忘掉工具本身。对我来说，一个 Markdown 文件加一条命令，已经足够让我把注意力留在文字上。这大概就是我能给「顺手」下的最好定义。
